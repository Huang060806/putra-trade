## 1. 表清单总览（12 张）

| # | 表名 | 对应课程表 | 作用 | 关键差异 |
|---|------|-----------|------|---------|
| 1 | `employee` | employee | 平台管理员 | 结构完全一致 |

## 2. 表关系图

```
employee (独立的管理员体系)
   │
   └── 处理 ──► report ◄── member (reporter_id 举报人)

category ──1:N──► item ◄──N:1── member (seller_id 卖家)
                    │
                    ├──1:N──► item_image
                    └──1:N──► orders ◄──N:1── member (buyer_id 买家)

member ──1:N──► favorite ──N:1──► item     (多对多中间表)
member ──1:N──► want ──N:1──► item         (多对多中间表, 点"我想要")
member ──1:N──► meet_spot
member ──1:N──► message
```

一个商品的一生：
`发布 → 敏感词扫描 → (干净: status=1 在售 / 命中: status=4 待审核，进后台人工审查)`
`1 在售 → 被下单/被预订(status=2 交易中) → 卖家点"标记为已售出"或买家确认完成(status=3 已售出)`
违规/主动下架 → `0 已下架`，卖家可重新上架。已售出不再出现在列表，买家在"我想要的"里能看到状态变更。

## 3. 关键设计决策（重点看这里）

### ① 为什么没有 order_detail 子表？
外卖一单多点菜，需要子表明细；二手交易**一单只买一件**。硬套课程的 order_detail 反而别扭。
但课程要教的知识点没丢：order_detail 本质是「订单创建时把商品信息**快照**下来」——我们把快照直接放进 orders 主表（`item_title`、`price`、`meet_spot_info`），效果相同。

> 面试考点：为什么订单里要存价格快照，而不是每次 JOIN item 表实时取？
> 答：商品价格会改、标题会改、甚至记录会被删，历史订单必须定格在下单那一刻。

### ② 商品 status 为什么是 5 态而不是课程的 2 态？
课程菜品只有「起售/停售」。二手商品有交易流转 + 审核流转（2026-09-03 按你的要求确认）：

```
发布 ──敏感词扫描──► 干净: 1 在售
                └──► 命中: 4 待审核 ──后台人工审查──► 通过: 1 在售 / 驳回: 0 已下架

1 在售 ──有人下单/卖家标记预订──► 2 预订/交易中 ──卖家"标记为已售出"──► 3 已售出
 │                                   │
 │                                   └──取消/超时──► 回到 1 在售
 └──► 0 已下架（主动下架 / 违规下架 / 审核驳回，可重新上架）
```

- 卖家手动「标记为已售出」→ status=3，商品立即从列表消失，**不再收到"想要"和下单打扰**——这是你提出的关键诉求。
- 买家在「我想要的」列表里能实时看到状态变化（在售→交易中→已售出），决定要不要继续等。
- Day4 的「起售停售」练习照常能做（切换 0/1）；状态机是 Phase 4 下单闭环的核心，也是简历亮点。

### ③ 为什么 password 字段是 VARCHAR(72)？
课程用 MD5（32字符）。我们建议升级 **BCrypt**（60字符，自带盐值，抗彩虹表）。
字段长度提前留好，Phase 1 直接用 BCrypt 不用改表。这是可以写进简历的细节："识别出课程方案 MD5 的安全隐患并升级 BCrypt"。

### ④ member 为什么要求学号 + UPM 邮箱双唯一？
- 学号唯一 = 一个学生一个账号
- UPM 邮箱验证码注册 = 校园身份门槛（校外人员进不来）——这是平台业务上最核心的壁垒
- 对应课程知识点：微信 code 登录的本质就是"用可信第三方证明你是谁"，我们换成"用校园邮箱证明你是 UPM 的人"

### ⑤ 金额为什么用 DECIMAL(10,2) 不用 DOUBLE/Float？
经典面试题：浮点数有精度误差，钱不能算错。`0.1 + 0.2 != 0.3`。
金额一律 DECIMAL，代码里对应 Java 的 `BigDecimal`。

### ⑥ create_user 和 seller_id 并存会不会矛盾？
- `seller_id` 是**业务归属**：谁发布的商品（永远指向 member）
- `create_user` 是课程公共字段填充（MetaObjectHandler）的**操作审计**：这条记录最后是谁操作的
- 管理员下架违规商品时 create_user=员工id、seller_id=学生id，两个字段各有用途

### ⑦ 索引怎么定的？——按查询场景倒推
| 场景 | 索引 |
|------|------|
| 首页"最新在售"：WHERE status=1 ORDER BY create_time | `idx_status_create(status, create_time)` |
| 首页"热度排序"：WHERE status=1 ORDER BY want_count | `idx_status_want(status, want_count)` |
| 分类页浏览 | `idx_category(category_id)` |
| "我发布的"/"我卖出的" | `idx_seller(seller_id)` / `idx_buyer(buyer_id)` |
| 收藏/想要去重 | `uk_member_item(member_id, item_id)` 唯一索引顺便防重复插入 |
| 订单号查单 | `uk_order_no(order_no)` |
| 后台举报队列：按类型+状态筛 | `idx_type_status(target_type, status)` |

原则：不是每列都加索引，而是先想清楚高频查询长什么样。

### ⑧ 冗余字段 seller_id 违反第三范式吗？
违反，但是**故意的**。"我卖出的订单"如果只存 buyer_id 就得 JOIN item 再拿 seller_id，多一次联表。空间换时间是冗余的正当理由（前提：这个值几乎不会变——买家不会变，成立）。

### ⑨ want_count 为什么冗余存在 item 表？高并发怎么办？（2026-09-03 新增 + 复审结论）
「按想要人数热度排序」是高频列表查询。如果每次 ORDER BY (SELECT COUNT(*) FROM want ...) 或 JOIN + GROUP BY，列表页性能会很难看。
所以 item 表冗余 `want_count`，`idx_status_want(status, want_count)` 索引直接支撑热度排序。

**并发与一致性结论（2026-09-03 你提问后定稿）：初期直接打 MySQL，不上 Redis 计数。**
理由：
1. `UPDATE item SET want_count = want_count + 1 WHERE id = ?` 本身就是**单行原子操作**，InnoDB 行锁持锁时间是微秒级，校园平台的并发量远打不到锁竞争瓶颈。
2. 正确性由 `want` 表的唯一索引 `uk_member_item(member_id, item_id)` 兜底：重复点"想要"会撞唯一索引，应用层捕获后按幂等成功处理，**want_count 永远不会因重复点击虚增**。
3. 同事务写入：INSERT want + UPDATE want_count 在同一事务提交，要么都成功要么都回滚，不存在"表里有记录但计数没加"的中间态。
4. Redis INCR + 定时回刷是日 PV 百万级点赞场景的方案，引入它要多处理缓存击穿、回刷失败补偿、重启丢数据三个新问题——现在的规模是拿复杂度换用不到的性能。

> 面试如果被问"并发高了怎么办"，标准答案就是你自己想的那个方向：Redis 原子计数 + MQ/定时任务异步落库 + 定期对账。能讲出"为什么现在不用"比直接用更值钱。

### ⑨-b 防刷规则：卖家不能点自己商品的"想要"（2026-09-03 新增）
- 应用层硬校验：`item.seller_id == 当前用户id` 时拒绝插入 want（接口返回"不能想要自己的商品"）。
- want_count 因此天然不可能被卖家自刷；唯一索引再保证"一个买家对一件商品最多 +1"。

### ⑩ 违规下架理由存在哪？卖家昵称要不要冗余？（2026-08-23 新增）
- **违规下架理由**：只写入 `message` 表（type=3 平台通知）推送给卖家，**不在 item 表加字段**——商品重新上架后该信息无保留价值，但消息历史可追溯。
- **商品卡片显示卖家昵称**：不冗余存储，列表查询 JOIN member 取 `nickname` 即可。等数据量大到有性能压力时再考虑缓存/冗余——到时候正好是 Redis 缓存章节的实战案例。

### ⑪ "想要"和"收藏"为什么是两件事？（2026-09-03 新增）
语义不同：
- **favorite 收藏** = "先码住，再看看"，轻操作，不通知卖家。
- **want 想要** = "我有购买意向"，重操作：① 解锁卖家微信/WhatsApp（两阶段私聊方案的第一阶段）② 卖家收到 type=4 通知 ③ want_count+1 影响热度。
面试时这个"轻意向/重意向分离"是个可以讲的业务建模亮点。

### ⑫ 举报为什么一张表装两种对象？（2026-09-03 新增）
商品举报和用户举报的字段几乎一样（举报人、原因、凭证、处理状态），只有"举报对象"不同。
用 `target_type(1商品 2用户) + target_id` 一张表装下，比两张表少一半重复代码，后台举报中心也只需要一套列表/处理接口。
代价：target_id 没有外键语义（指向哪张表取决于 type）。这是典型的"多态关联"取舍，可讲。

### ⑬ 敏感词过滤怎么做？（2026-09-03 新增 + 复审改判：命中不硬拒，进人工审查）
两层防护：
1. **自动层**：发布/编辑商品时，后端用 **DFA 算法**（字典树）对 title+description 扫描 `sensitive_word` 词库。
   **命中不硬拒绝**（2026-09-03 按你的决定改）：商品落库为 `status=4 待审核`，`audit_remark` 记录命中词，进入后台审核队列，和举报队列并列展示。管理员通过 → 1 在售；驳回 → 0 已下架并通知卖家（含命中词说明）。
   好处：不误伤正常商品（比如"讲义"里夹了误判词），卖家体验好；审核入口和举报统一，后台一套界面管两件事。
2. **人工层**：`report` 举报 + 后台审核下架，兜住漏网之鱼。

词库加载进内存（启动时加载 + 后台改词后刷新，正好练 Spring Cache）。
"DFA 前置扫描 + 待审核状态机 + 举报闭环"是内容平台的标配架构，简历可写。

### ⑭ 统计看板要不要建统计表？（2026-09-03 新增）
**不建**。每日新增用户、发帖量、违规处理数都是"按 create_time 分组 COUNT"的现成查询：
```sql
SELECT DATE(create_time) d, COUNT(*) FROM member GROUP BY d;   -- 每日新增用户
SELECT DATE(create_time) d, COUNT(*) FROM item GROUP BY d;     -- 每日发帖量
SELECT DATE(handle_time) d, COUNT(*) FROM report WHERE status=1 GROUP BY d;  -- 每日违规处理
```
数据量上来后如果看板查询变慢，再加"每日快照表"做预聚合——那是后期优化，不是现在的问题。ECharts 直接吃这些接口。

### ⑮ 个人中心的"我的发布/我想要的/资料设置"需要新表吗？
不需要，全部是现有表的查询入口：
- 我的发布 = `item WHERE seller_id=?`（编辑/改价/标记售出/删除都是 item 的写操作）
- 我想要的 = `want JOIN item`（列表里能看到商品当前 status，满足你"状态更新可见"的要求）
- 资料设置 = 更新 member 的 `wechat / whatsapp / phone / dorm_area / avatar / nickname`

### ⑯ 顶部搜索栏怎么做？（2026-09-03 复审新增）
列表接口统一加 `keyword` 参数，后端 `WHERE title LIKE CONCAT('%', #{keyword}, '%')`（顺带搜 description）。
- 现阶段：title 走 LIKE 即可，配合 `idx_status_create` 过滤在售商品，数据量万级以内无压力。
- 注意：LIKE '%xx%' 前导通配符走不了索引——这是**故意接受的**，路线图第 6 节已把「MySQL LIKE → Elasticsearch 全文搜索」列为后期加分项，面试时"我知道瓶颈在哪、知道升级路径"就是完整答案。
- 搜索栏交互：顶部常驻，关键字 + 分类 + 交货地点标签 + 排序（最新/价格升/价格降/热度）四个维度组合筛选，一个接口搞定。

### ⑰ 买家看到的卖家联系方式：实时查还是快照？（2026-09-03 复审定稿）
**实时查 member 表最新值，不做快照。** 理由：
1. 联系方式是**沟通工具不是交易凭证**。买家想要的是"现在能联系上卖家"——卖家换了微信号，买家还看着旧号加不上人，体验是坏的。
2. 争议追溯的凭证在 `orders` 表：`meet_spot_info` 快照（含下单时的联系人和电话）已经定格了交易当下，这才是纠纷时的证据链。want 只是意向，没产生交易，没有可追溯的"争议"。
3. 实现上零成本：want 列表 JOIN member 取 wechat/whatsapp 即可，不用加字段、不用维护快照一致性。
卖家改联系方式后，所有意向买家下一次打开"我想要的"看到的就是新号——这正是想要的行为。
